The Theory
Nyquist-Shannon: your sample rate defines what you can see
To faithfully reconstruct a signal you must sample at ≥ 2× its highest frequency — events shorter than your sample interval are permanently invisible

The theorem, plainly: a sampler running at fs can only detect events lasting longer than 2 / fs. Below that threshold the event produces zero samples — it does not exist to your monitoring system. One lone sample is not a measurement, it is noise.

Applied to networking

60 s poll Only detects events lasting ≥ 30 seconds. A NIC ring overflow that clears in 50 ms registers as zero data points — completely silent.
1 s poll Detects events lasting ≥ 500 ms. TCP micro-bursts (100–200 ms) and softirq spikes still vanish between samples.
10 ms nyquist Detects events lasting ≥ 20 ms. Captures ring overflows, softirq saturation spikes, and TCP burst drops with 5× headroom above the Nyquist limit.
Why this matters for the case study ahead: the RSS queue imbalance manifests as 50–80 ms CPU softirq saturation bursts on 8 cores. A 1-second poller has a ~7% chance of catching any single spike. nyquist catches every one — and correlates them with queue depth and retransmit events in the same 10 ms window.
Design Principles
Six decisions that separate observability from monitoring
Each principle addresses a specific failure mode in traditional monitoring tools
📡
Sample at the Nyquist limit
10 ms sampling interval, not a 60 s poll. An event that clears before the next sample never happened, as far as your monitoring system is concerned. Most network incidents live in the 50–500 ms range.
100 Hz sample rate · 50 Hz Nyquist limit
📊
Preserve the distribution
Averages erase the tail — and the tail is where incidents live. nyquist feeds every 10 ms observation into a sliding HDR histogram and exports p50 / p90 / p99 / p99.9. Nothing is discarded.
60 s window · 6,000 samples per metric
🧬
Kernel-authoritative data
Read from /proc and eBPF tracepoints directly. User-space wrappers can be stale, batched, or wrong. The kernel counter is the ground truth — go as close to the source as possible.
procfs · eBPF · perf_events · netlink
⏱
Temporal alignment
Every metric — NIC queue depth, TCP RTT, CPU softirq, memory pressure — is sampled on the same 10 ms wall-clock tick. Cross-layer causality is only valid when metrics share a timestamp.
single scheduler · one clock source
🦀
Zero external dependencies
A single statically-linked Rust binary. No agents, sidecars, JVM, or Python runtime. Drop it on any Linux host and it runs immediately. Gracefully degrades to procfs-only without root privileges.
root: +eBPF +perf · non-root: procfs only
🔀
Decouple collection from export
Collection runs at 100 Hz; export pushes every 10 s. A slow VictoriaMetrics write or ClickHouse insert can never stall a sensor read. Rate mismatch between collection and reporting is a deliberate design goal, not an accident.
collect 100 Hz · push 0.1 Hz

The Mechanism
From a raw kernel counter to a stable p99
Five stages turn ~6,000 instantaneous rate samples per minute into one percentile readout — refreshed continuously
1 every 10 ms
Read & rate
Each sampler reads its source (/proc/net/dev) and converts the counter delta into an instantaneous rate.
rate = Δcounter / 0.010 s
→ bytes / second

2 100 ms slice
Bucket into a slice
~10 rate values land in each 100 ms slice. A slice is a fixed inline array — it stores raw values, not bucket counts. The HDR histogram is built on-demand at merge time.
~10 samples → 1 slice
O(1) insert
▶
3 60 s window
Slide the window
A ring buffer of 600 slices. Every 100 ms the oldest slice is evicted and a fresh one appended — always the last 60 seconds.
600 slices = 60 s / 100 ms
▶
4 on snapshot
Merge & read
All 600 slices are summed into one aggregate histogram, then p50 / p90 / p99 / p99.9 are read straight from it.
Σ buckets → percentiles
▶

cpu1, cpu3, cpu47… all pinned at 100–108% softirq. A CPU cannot exceed 100% — these are fully saturated.
184 CPUs idle while 8 do all the work. The system has 192 cores but only 8 are engaged.
Why these CPUs? NIC queue N → CPU N via IRQ affinity. The question becomes: why only queues 1, 3, 5, 13, 23, 35, 37, 47?
Observation 3 of 3
Only 8 of 63 RSS queues are active — Toeplitz hash collision
nyquist monitors all 63 per-queue packet rates at 10 ms. The imbalance pattern is the key diagnostic clue.

p99 RX pps per queue (Mpps) — only active queues

Traffic share per queue — q47 + q3 carry 37%

Toeplitz hash with 10 streams (same src/dst IP, varying src port) produces only 8 unique hash outputs → 8 queues → 8 CPUs.
Imbalance within queues: q47 carries 19%, q3 carries 18%. Two CPUs handling 2× their fair share while already saturated.
55 queues completely idle. The NIC is capable of 63× the per-queue throughput. The bottleneck is entirely in how flows are steered.
Root Cause Analysis
Ruling out false positives — only one true bottleneck
nyquist monitors all potential bottlenecks simultaneously, eliminating guesswork
🔴 CPU softirq (hot cores)
100–108% — SATURATED → this is the ceiling
🔴 RSS queue utilisation
8 / 63 (13%) — forces all load onto 8 CPUs
🟢 TCP CWND vs BDP
177% of BDP — window is ample, not limiting
🟢 tcp_rmem ceiling
31% used (ceiling = 156 Gbps at 394µs RTT)
🟢 NIC ring buffer
0 rx_missed, 0 rx_out_of_buffer
🟢 TCP retransmits
6427 over 381s — negligible rate
🟢 NUMA locality
NIC on socket 0, all active CPUs on socket 0
🟢 MTU (contributes)
1500B MTU → 3.9 Mpps — high per-packet CPU cost amplifies saturation
